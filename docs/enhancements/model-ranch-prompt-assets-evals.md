# Enhancement: the Model Ranch, prompts as assets, continuous evals, and the queue platform under them

**Status:** approved for implementation · **Drafted:** 2026-10-25, through four review rounds (architecture, code, operator; skeptic + architecture twice) · **Executed by:** an agent session following "Working rules" below, PR by PR.

**This document is the whole brief.** The agent executing it has no memory of the discussions that produced it. Everything it needs is here or in the files this document names. Where it says "decided", do not reopen the decision; where it says "guess", it is a mistake in this document: stop and ask the owner.

## 1. Context

BloggerBear prompts Bedrock in ~38 templates across ~25 call sites (daily cycle, research tick, rewrite, reviews, comment screening, reflection, gear, musings, reviewer bear, vision triage, model-catalog web pricing, the ops agent). They are inline code constants: changing one needs a code deploy, versions aren't tracked, and nothing measures which model or prompt produces good results. Model selection is random, price-based or access-based. Scheduling is one pair of EventBridge schedules per topic with hand-set stagger slots, which stops scaling past about twelve topics, and nothing caps how many model calls run at once.

This adds, in order: **a queue platform** (one dispatcher, a FIFO work queue, one concurrency knob, usable at 20–100 topics), **prompts as assets** (versioned prompts in S3 with A/B splits and a code fallback, published by their own gated workflow), **continuous evals** (scored events to an `evals` log group, rolled up into DynamoDB) and **the Model Ranch** (ratings on the models table, a rotation guard that filters, culling in proposal mode, forgive/punish, model purpose tracking, a calibrated LLM judge, offline scoring runs, a human review CLI, MCP/Alexa+ tools, two dashboards).

Superseded: [`dispatcher-sqs-enhancement.md`](dispatcher-sqs-enhancement.md) step 3 (removing per-topic scheduling). Schedule mode stays as the permanent undo.

**Prompts**
- Prompts live in this monorepo under `prompts/`, published by their own workflow (`.github/workflows/prompts.yml`) to a dedicated S3 bucket. Terraform owns the bucket, never the objects. Not Ansible.
- The workflow's own gates: prompt lint and guardrails, PII denylist, gitleaks, trufflehog, pytest, trivy, checkov.
- Dev publishes on merge to `dev`. **Production publishes under a second GitHub environment, `production-prompts`** (required reviewer: the owner; deployment branch `dev`), which the owner creates once (runsheet step; never changed by a code PR). Also on every `release: published` under `production`, so prompts and code never drift. Every release therefore needs two approvals (deploy + prompts); accepted.
- The publisher writes the prompt-hash table; the hash check is always on when assets are on (no separate flag).
- Rollout is a declarative reconcile: the repo's `latest/` folders are the desired state; one file = the prompt; two or more = an A/B split; each publish is a release.
- Failures during a release are acceptable: `get_prompt` falls back to vanilla.
- **Code-only prompts (versioned vanilla, never an asset):** the ops agent's system prompt (its role's isolation rule must not widen), the compliance review (rule 3's gate), vision triage (safety rules), comment screening (PII rules), the judge rubric. Their `vanilla:vN` versions are recorded in lineage like any other.
- Vanilla prompts may be edited by code PR; byte matching is a migration-only check, not a standing gate.

**Evals and ranch**
- Dedicated `evals` log group, 120-day retention. Day totals, windows summed on read. Gates = spec thresholds + `min_events`. A/B = one draw per run. Steering in the judge and fresh-data review only. Judge ≠ author. Reader votes score models in reports and cells but never gate. Culling is proposal-then-apply. Discovery's `prune_mode` ordering is untouched. The rewrite picker ranks suitable, active models by performance. Offline scoring runs from the CLI through a queue, never touching assets.
- **Queue platform first, for the whole platform.** Plain SQS consumers at low concurrency; no yield rules, pollers or leases. Fixed global jobs (reviewer bear, model catalog, stats rollover, Cost Explorer poll, weekly reflection, musing feedback, eval jobs' own schedules) stay on EventBridge schedules.
- Pipeline-health gets a model-catalog counter row (discovered, pruned, classified, denied, repriced, reverted).

## 3. Deviations from the owner's spec, each with its reason

1. `get_prompt(lambda_id)` with one `latest/` per Lambda would mix a Lambda's prompts → `get_prompt(prompt_id)`, `prompt_id = "<lambda_id>/<prompt_name>"`, S3 `<lambda_id>/<prompt_name>/latest/<version>.txt`; version from the S3 object tag `version`, as specced.
2. A static S3 string can't carry runtime data or keep guardrails → templates with `{{name}}` values and `{{locked:name}}` blocks filled from code; any validation failure → vanilla + a `prompt_fallback` evidence line.
3. Migration must not change pipeline text → the ~174 exact-text tests stay unchanged in each migration PR; afterwards `vanilla_version` + pinned sha256, no standing byte gate.
4. The flush chain (daily→weekly→monthly) double-counts across month boundaries and isn't retry-safe → day totals SET idempotently, windows summed on read. The models table still carries the spec's `daily_perf`, `weekly_perf`, `monthly_perf`, `total_perf`.
5. A daily cron can't give "today so far" → hourly rollup from a watermark.
6. The spec's event has no id → `event_id` added (§4.3); the rollup dedups by it. `schema`, `subject`, `topic_id`, `source` added (ids, never text).
7. Stored `model_roles` drift → written for display, re-derived live for culling.
8. A hand-deleted model is re-added by `discover` → cull archives then deletes (the prune path); rollup updates are conditional on `attribute_exists`.
9. Self-judging → judge ≠ author, always.
10. `reviewed_by` would be personal data (rule 1) → role codes `human`|`judge`; agreement is computed from paired events in the evals log by `subject` (Findings expire in 14 days).
11. Steering in compliance would let topic text loosen the publish gate (rules 3, 4) → judge and fresh-data review only.
12. A separate pipeline straight to production would bypass the release rule → the `production-prompts` environment with the owner's required review.
13. The spec's rotation gates on raw sums favour exposure → `min_events` per window, mean per event shown; the picker's statistic excludes Completion.
14. Dedicated `VERIFY_PROMPT_HASHES` flag dropped (the owner: running without it is riskier; one knob fewer).
15. "Model-only" reasons still carry prompt ids and count in model×prompt cells, not in prompt aggregates.

## 4. Data contracts (the glossary an implementer needs)

### 4.1 Prompt template grammar
- Placeholders: `{{name}}` (a value from code) and `{{locked:name}}` (a block from code the asset cannot change). Regex, strict: `\{\{(locked:)?[a-z_]+\}\}`; anything else, including `{"verdicts"` in reviewer/model-catalog vanillas, is literal text.
- Rendering is single-pass and never re-scans values (a draft containing `{{x}}` stays literal).
- Rules checked at load: every `required` placeholder present, no unknown placeholder, every `locked` block exactly once and in `locked` order, **locked blocks form the template's tail** (free text may precede, not follow), the template's size ≤ `max_chars`. The template is measured, not the rendered text: the caller's values would make the vanilla just as long, so a render-size fallback cures nothing. A spec's `max_chars` must therefore be at least its vanilla's length (`PromptSpec` refuses less). Failure → vanilla with a `fallback_code` from: `s3_error`, `no_files`, `no_version_tag`, `too_large`, `missing_placeholder`, `unknown_placeholder`, `locked_missing`, `locked_order`, `hash_unapproved`, `hash_lookup_failed`, `decode_error`, `paused`, `assets_off`.
- Optional blocks are values whose empty form is zero bytes; a locked block may legally render empty (e.g. financial guidance on a non-financial topic).
- `PromptSpec(prompt_id, vanilla: str, vanilla_version: str, vanilla_sha256: str, required: frozenset, optional: frozenset, locked: tuple, max_chars: int, asset: bool = True)`. `asset=False` specs never touch S3 and always report `vanilla:<vanilla_version>`.
- `get_prompt(prompt_id, values: dict, locked: dict) -> Prompt(text, prompt_id, version, source: "asset"|"vanilla", fallback_code: str|None)`; `vanilla_prompt(prompt_id) -> str`; `bind_run(key: str|None)` (a contextvar, like `evidence.bind`). The arm is `sha256(f"{run_key}|{prompt_id}") % n` over the sorted file keys; random when no key is bound.
- `version` values: an asset's S3 tag (`v2`), or `vanilla:v1`.
- sha256 = hex digest of the file's UTF-8 bytes with `\n` newlines.
- Per-container cache: the listing, tags, bodies by sha, hash rows; TTL 300 s.
- Run keys: daily cycle = `_run_id` (the execution id); rewrite = `rewrite_id`; research tick = the request id; API calls = the request id; judge/score = the item key.

### 4.2 Prompt storage
- Repo: `prompts/<lambda_id>/<prompt_name>/latest/vN.txt` (retired files → `prompts/<lambda_id>/<prompt_name>/archive/`). Filename = version. `prompts/README.md` states these rules.
- S3 bucket `<prefix>-<env>-prompts`: `<lambda_id>/<prompt_name>/latest/vN.txt` (tags `version`, `release`, `sha256`), write-once `<lambda_id>/<prompt_name>/versions/<sha256>.txt`, `releases/<release_id>.json`, `releases/current.json`. `release_id = <env>-<yyyymmddThhmm>-<short sha>`.
- Hash table `<prefix>-<env>-prompt-hashes`: PK `prompt_hash` (sha256 hex); attrs `prompt_id`, `version`, `release`, `approved_at`, `status` (`live`|`retired`), `retired_at`. No TTL. Written only by the publisher role. The Lambda accepts `live`, or `retired` with `retired_at` ≤ 300 s ago.
- Pause flags: `paused_versions` (a list of `<prompt_id>@<version>`) on the `prompts` row (`config_id = "prompts"`) of the model-config table, written by the admin API. Global kill switch: `prompt_assets` (`on`|`off`) on the same row.
- Write-once guard for `versions/`: a conditional `PutItem` on the hash row (`attribute_not_exists(prompt_hash)`) **before** the S3 upload. (`PutObject(IfNoneMatch)` is not in the pinned boto3 1.34.162.) The bucket is versioned, so a repeated key is recoverable anyway.
- Publish order, one list: (1) for each new file: conditional hash row (`status=pending`), upload to `versions/`; (2) set those rows `live` with the release; (3) sync `latest/` (add, then remove stale); (4) set the previous release's rows `retired` with `retired_at`; (5) write `releases/<id>.json` and `current.json`. Rollback = `git revert` + publish; the `release_id` workflow input sets `pinned_release` in `current.json`, which the publisher honours (re-running steps 2–3 for that release) until cleared. `current.json` is `{"release_id": "<the release in place>", "pinned_release": "<release_id>" | null}`; the names are `prompts.CURRENT_RELEASE_FIELD` and `PINNED_RELEASE_FIELD`, and a pin writes no new `releases/` record.
- Worst-case service of a superseded or paused version: 600 s (cache TTL + retire grace).

### 4.3 Eval event (one PutLogEvents message, JSON)
Fields and kinds (reuse `common/evidence.py`'s validators: code, id, model id, ISO time, number): `schema` ("evals/1"), `event_id`, `timestamp`, `model_id` (canonical), `prompt_id`, `prompt_version`, `performance` (`good`|`bad`|`neutral`), `rating_delta` (int), `reason` (code), `subject` (article id, or `<topic_id>#<captured_at>`), `topic_id`, `source` (the emitting Lambda's code), `by` (`human`|`judge`|`system`, optional). Free text is never emitted.
Example: `{"schema":"evals/1","event_id":"completion:a1b2:daily_cycle/draft","timestamp":"2026-10-25T03:04:05Z","model_id":"au.anthropic.claude-haiku-4-5-20251001-v1:0","prompt_id":"daily_cycle/draft","prompt_version":"v2","performance":"good","rating_delta":2,"reason":"Article Completion","subject":"a1b2","topic_id":"github-trending","source":"daily_cycle"}`

Writing: one log stream per container, name `<function>/<yyyy-mm-dd>/<container id>`; `botocore.Config(connect_timeout=1, read_timeout=1, retries={"max_attempts": 1})`; `emit()` never raises; in the public API it runs after the response is built.

`event_id` per reason (one event **per (subject, prompt_id)** for prompt-scoped reasons, so an article's several prompts each get their own event): `completion:<article_id>:<prompt_id>`, `rewrite:<rewrite_id>`, `vote:<feedback_id>`, `admin:<queue_id>:<decision>:<prompt_id>`, `judge:<subject>:<run_id>`, `human:<subject>:<ts>`, `offline:<run_id>:<item>:<combo>`, `adjust:<ts>:<target>`, `fallback:<request_id>:<prompt_id>`.

Scoring (`SCORING` in `common/evals.py`):

| reason | delta | applies to | gates? |
|---|---|---|---|
| Article Completion | +2 | model and each prompt in the article's lineage | yes |
| Article Rewrite | −2 | model | yes |
| User Feedback | ±1, or ±3 with a kept comment | model (cells too) | **no** |
| Admin Review | ±2 (a human's approve/reject) | model and prompts | yes |
| Research Review / Article Review | ±2 (judge) | model and prompts | only while calibrated |
| Human Review | ±2 | model and prompts | yes |
| Offline Review | ±2 (judge, `--record` runs only) | the scored combination | only while calibrated |
| Admin Forgive / Admin Punish | ±N, N ≤ 100 (`--allow-cull` for more) | the named model or prompt version | total only |
| Prompt Fallback | 0 | prompt version | counted, not scored |

`performance` must match the sign of `rating_delta` (`neutral` for 0). Votes reach prompt cells through the rollup joining `vote:*` to the subject's `completion:*` events by `subject`; the public API never loads lineage.

### 4.4 Evals table `<prefix>-<env>-evals` (PK `entity`, SK `sk`, no TTL, `protect_data` like app-data)
| entity | sk | attrs |
|---|---|---|
| `model#<id>` | `day#<yyyy-mm-dd>` | `perf`, `events`, `good`, `bad`, `by_reason` (map), `rolled_up_at` |
| `prompt#<prompt_id>#<version>` | `day#…` | same |
| `cell#<model>#<prompt_id>#<version>` | `day#…` | same |
| `adjust#model#<id>` / `adjust#prompt#<pid>#<ver>` | `ts#<iso>` | `delta`, `reason`, `by` (excluded from window sums; counted in `total_perf`) |
| `run#<run_id>` | `meta` / `item#<n>#<combo>` | run header: `status` (`queued`|`running`|`paused: spend cap`|`done`|`cancelled`), `estimate_aud`, `spent_aud`, `created_at`; items: `verdict`, `delta`, tokens, `cost_aud` |

### 4.7 Queue messages and names
- Research message body (FIFO `work.fifo`): `{"topic_id": "...", "job": "research", "force": false, "due_checked_at": "<iso>", "dispatched_at": "<iso>"}`; `MessageGroupId = topic_id`; `MessageDeduplicationId = <topic_id>:research:<yyyy-mm-ddTHH:MM>`. The research-tick handler ignores `job`; it evaluates `is_due` at `due_checked_at` (FIFO ordering makes a stale message harmless).
- Daily: no message. The dispatcher calls `StartExecution(stateMachineArn, name=f"{slug}-{local_date}-{n}", input='{"topic_id": "..."}')`. `local_date` in the topic's `daily_timezone`. `slug` = `topic_id` lower-cased with every char outside `[a-z0-9-]` replaced by `-`, max 40 chars; the pre-flight (Q2) refuses a topic whose slug collides with another's. The state machine's `NameTheRun` Pass state adds `$$.Execution.Id`, and `daily_cycle_handler._run_id` keeps working unchanged. Manual: `name=f"{slug}-{local_date}-manual-{HHMMSS}"`.
- Claims (conditional `UpdateItem` on the Topic row): daily `SET last_daily_dispatched_on = :today ADD daily_claim_n :one` with `attribute_not_exists(last_daily_dispatched_on) OR last_daily_dispatched_on <> :today`; research `SET research_claimed_at = :now` with `attribute_not_exists(research_claimed_at) OR research_claimed_at < :expiry` where `:expiry = now − research interval`. If the send/start fails after the claim, release it (`REMOVE` / set back).
- `ExecutionAlreadyExists` → treated as consumed (log line, no retry). Same name while RUNNING with identical input returns success; also fine.
- Eval message (`eval-work`): `{"job": "judge"|"score", "run_id": "...", "item": {...}, "combination": {"model_id": ..., "prompt_versions": {...}}}`.
- `dlq_handler`: a body with `job` is a queue job; it words the failure as `<job> job for topic_id=… failed` (today's text says daily_cycle for everything).

### 4.8 Cron matcher (`common/cron_match.py`)
Accepts exactly the shapes `stagger.staggered_expression`/`_shift_hours` can emit **or pass through** from an operator: minutes `M` (whole) or `*/N` or a list; hours `*`, `H`, `*/N`, `a/N`, `H1,H2,…`, `A-B` (may wrap midnight: `22-2`), optional `/N` step on a range; day-of-month `*`, `?`, `1/N`, `D`; month `*`; day-of-week `*`, `?`, names list, range; year `*`. `rate(N minutes|hours|days)`. Refuses `at()` and anything else with a logged `dispatcher: cadence unparsable topic_id=… expression=…` line and the topic is skipped (never guessed); the Q2 pre-flight refuses such a topic before cutover; the admin API validates new cadences with it.
Rules: `rate()` research = every minute is a turn and `is_due` decides (the enhancement doc's rule); `rate()` daily = refused. "Turn passed" = `(hour, minute)` tuple comparison in the topic's zone, so a spring-forward 02:30 fires at 03:00 and a fall-back repeat is stopped by `last_daily_dispatched_on`. Research turns are matched over `(last_tick, now]` (the dispatcher stores `last_tick` on the pipeline row) so one failed dispatcher invocation costs nothing. A daily cadence with several hours (`9,21`, `*/4`) dispatches **once per day** (first turn passed); this is a documented behaviour change from the Scheduler, which fires each.

### 4.9 Picker and report statistic
good = events with Δ>0, bad = Δ<0, over judge, human, feedback, rewrite and admin events (Completion and Fallback excluded). Rank models with `n ≥ min_events` by the Wilson lower bound of good/(good+bad) (copy `wilson(k, n)` from `scripts/vision_eval_scoring.py:46` into `common/evals.py`; `scripts/` is not in the Lambda package), then by blended price, then id; models below `min_events` follow, by blended price. Tables show `n` and the interval.

## 5. Architecture as built

### 5.1 `infra/modules/work-queue` (Q1)
Resources: `aws_sqs_queue.work` (`<prefix>-<env>-work.fifo`, FIFO, `content_based_deduplication = false`, visibility 720 s, redrive `maxReceiveCount` 3 → `work_dlq`), `aws_sqs_queue.work_dlq` (`<prefix>-<env>-work-dlq.fifo`), `aws_lambda_function.dispatcher` (`<prefix>-<env>-dispatcher`, timeout 60 s, own log group inside the module with the `depends_on` line form, like `infra/modules/vision-worker/main.tf:228-241`), `aws_scheduler_schedule.dispatcher` (`rate(1 minute)`), `aws_lambda_event_source_mapping.research_tick` (on `work.fifo`, `batch_size 1`, `scaling_config { maximum_concurrency = var.worker_concurrency }`, min 2), `aws_lambda_event_source_mapping.work_dlq` (on `work_dlq` → the `dlq_handler` function ARN passed in), alarms (dispatcher errors/throttles; `work.fifo` `ApproximateAgeOfOldestMessage` > 900 s; both DLQ depths; `dispatcher_tick` metric filter with `treat_missing_data = breaching` over 15 min). ### 5.4 Flows (numbered, for tracing)
**Article:** dispatcher tick → `cron_match` says the daily turn passed → conditional claim (`last_daily_dispatched_on`, `daily_claim_n`) → `StartExecution` named `<slug>-<date>-<n>` → `NameTheRun` adds `execution.id` → `daily_cycle_handler` (`_run_id` = execution id; `already_written` check) → article stored → `_stored` emits one `Article Completion` event per prompt in the lineage (`completion:<article>:<prompt_id>`) → `evals` log → hourly rollup → day rows for `model#`, `prompt#…`, `cell#…` → `*_perf` on the models row → next `resolve_model` filters gated candidates before its random draw. Loss points: `emit()` failure (logged, event lost: acceptable), rollup lateness (`late_dropped` counter, visible in `evals status`).
**Vote:** public API `_submit_feedback` → `put_feedback` → response → `emit(User Feedback, subject=article_id)` (no prompt) → rollup joins to the article's `completion:*` events by `subject` → `model#` and `cell#` day rows (not `prompt#`; not gates) → `prompt_metrics`.
**Offline run:** `admin_cli evals score` → `POST /evals/runs` (validate: judge ≠ every candidate model, all `suitable(TEXT)`, sample 1–50; estimate = items × combos × 2 drafts + 1 judge call, priced from the registry; refuse over remaining daily cap) → CLI prints the estimate and environment, asks y/N (refuses over `score_max_cost_aud` without `--yes`; `--record` needs `--yes`) → `run#meta` + one `score` message per item × combination → the ESM consumer renders the candidate (asset version from `versions/`, or vanilla), drafts with the candidate model, drafts the live version (cached per item in `run#`), the judge compares (judge ≠ both) → `run#item` row (+ `Offline Review` event if `--record`) → `evals runs get` reads progress from the item rows.
